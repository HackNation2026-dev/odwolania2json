**2. Jak zbudować trudny zbiór z poprawnymi odpowiedziami**

Najpierw zamroźcie loader: referencje bazowe + poprawki pięciu odwołań **19, 23, 25, 44, 55**, zgodnie z `U`. Mapowanie nazw PDF/JSON jest opisane w `docs/07-decyzje/ADR-002-decyzje-po-recenzji.md`.

| Przekształcenie | Co zrobić z referencją |
|---|---|
| Rasteryzacja, kompresja, szarość, umiarkowany szum/rozmycie | Zachować, **jeśli wartości pozostają czytelne** |
| Obrót, przekrzywienie z zachowaniem całej strony | Zachować |
| Zastąpienie wybranych stron skanami | Zachować, jeśli zachowano wszystkie strony i treść |
| Wstawienie pustej strony, zmiana metadanych/nazwy pliku | Zachować; przesunąć jedynie lokalizacje dowodów |
| Dodanie błędnego niewidocznego OCR przy poprawnym obrazie | Zachować; to test odporności na błędną reprezentację |
| Pieczątka/podpis | Zachować tylko po sprawdzeniu, że nie usuwa dostępności wartości |
| Obcięcie, zaczernienie, usunięcie strony | Przejrzeć **wszystkie wystąpienia** dotkniętych pól i sporządzić nową referencję |
| Zmiana zapisu tej samej daty/kwoty/rachunku | Zachować wartość kanoniczną; sprawdzić wszystkie powtórzenia |
| Nowa treść, brak pełnomocnika, nowy mocodawca | Nowy PDF i nowa referencja, sprawdzane razem |
| Połączenie kilku dokumentów | Osobny test diagnostyczny do czasu ustalenia reguły jednego wyniku |

**Obcięcie strony nie oznacza automatycznie `null`.** Pole może występować ponownie w uzasadnieniu. Nie zmieniajcie też referencji na `null` dlatego, że wasz OCR czegoś nie odczytał.

Dla wariantów destrukcyjnych rozróżniajcie poza ocenianym JSON-em: „nieobecne”, „zasłonięte”, „nieczytelne”, „sporne”. Przypadki bez jednoznacznej odpowiedzi trzymajcie poza głównym wynikiem F1.

Proponuję:

- Podział **30 spraw do rozwoju / 10 do walidacji / 20 zamrożonych do testu**. Wszystkie dokumenty i pochodne jednej sprawy pozostają razem.
- Sześć podstawowych wariantów każdego dokumentu: skan dobry, skan średni, obrót, mieszany, błędny OCR, dodatkowa/pusta strona.
- Osobne mutacje treści pokrywające rzeczywiste luki z tabeli.
- Co najmniej trzy niezależne układy dokumentów: inne nagłówki, tabele, kolejność sekcji i łamanie stron. **Rasteryzacja LAPFormalDoc nie usuwa przeuczenia na jego układzie.**
- Zamrożone parametry i ziarna testowe; przynajmniej jeden sposób degradacji niewykorzystywany przy strojeniu.
- Losowe nazwy plików; referencje i identyfikatory źródłowe niedostępne dla ekstraktora.

Jeśli zespół już analizował wszystkie sprawy, taki podział będzie kontrolą regresji i odporności, ale nie całkowicie niezależnym testem generalizacji.

**3. Realistyczne generowanie i ocena `syntetyczne.py`**

Poniższe narzędzia proponuję **wyłącznie do generatora testów**.

| Narzędzie | Instalacja i licencja | Zastosowanie |
|---|---|---|
| Pillow | `pip install pillow`; MIT-CMU | Rozdzielczość, kompresja, rozmycie, składanie obrazów |
| OpenCV headless | `pip install opencv-python-headless`; wrapper MIT, OpenCV Apache-2.0; dodatkowe licencje binariów | Perspektywa, deformacja, morfologia, nierównomierne oświetlenie |
| Augraphy | `pip install augraphy`; MIT | Procesy druku, papieru, ksero, faksu |
| ReportLab + pypdf | `pip install reportlab pypdf`; BSD / BSD-3-Clause | Składanie PDF, tekst niewidoczny, łączenie i wymiana stron |
| pypdfium2 | `pip install pypdfium2`; Apache-2.0/BSD-3-Clause, PDFium i zależności mają własne licencje | Opcjonalny renderer generatora, gdy chcecie uniknąć systemowego Popplera |

Źródła: [Pillow](https://pypi.org/project/Pillow/), [OpenCV i licencje składników](https://pypi.org/project/opencv-python-headless/), [Augraphy](https://github.com/sparkfish/augraphy), [ReportLab](https://pypi.org/project/reportlab/), [pypdf](https://pypi.org/project/pypdf/), [pypdfium2](https://pypi.org/project/pypdfium2/).

Po instalacji takie generowanie może działać offline, na lokalnych zasobach. **Nie deklaruję sprawdzonej instalacji całego zestawu na Pythonie 3.13**: dokumentacja Augraphy wymienia testowane wersje 3.8–3.11. Dlatego podstawowy generator oparłbym na Pillow/OpenCV, a Augraphy potraktował jako opcję po krótkim sprawdzeniu zależności. [Dokumentacja instalacji Augraphy](https://augraphy.readthedocs.io/en/latest/doc/source/installation.html).

| Proces | Zalecana symulacja |
|---|---|
| Druk→skan | Render 300 dpi → drobne ubytki/rozlanie tuszu → tekstura papieru i nierówny kontrast → skan 150/200/300 dpi → kompresja |
| Ksero | Dwa–trzy kolejne przebiegi: progowanie, ubytki cienkich kresek, pogrubienie innych, pasy i przesunięcie kartki |
| Faks | Próbkowanie anizotropowe, obraz jednobitowy, ubytki linii i nagłówek transmisji; opcjonalnie `Faxify` |
| Telefon | Perspektywa czterech narożników, tło poza kartką, cień, balans bieli, rozmycie kierunkowe, JPEG; osobno wygięcie kartki |
| Dokument mieszany | Naprzemienne strony tekstowe i skany; również istotny fragment jako obraz **na stronie zawierającej tekst** |
| Błędny OCR | Obraz poprawny, tekst niewidoczny z błędami cyfr, polskich znaków, kolejności i brakującymi wierszami |

OpenCV udostępnia transformacje perspektywiczne; Augraphy ma m.in. `Faxify`. ReportLab pozwala sterować trybem renderowania tekstu. [OpenCV](https://docs.opencv.org/4.x/da/d54/group__imgproc__transform.html), [Faxify](https://augraphy.readthedocs.io/en/latest/doc/source/augmentations/faxify.html), [ReportLab](https://docs.reportlab.com/reportlab/userguide/ch2_graphics/).

**Fakty i ograniczenia obecnego generatora** — źródło: `E/narzedzia/syntetyczne.py`:

- „Ksero” to zasadniczo jednolite szare tło, niezależny szum i obrót. Brakuje utraty/pogrubienia kresek, pasów oraz kolejnych generacji kopii.
- Obrót przez `expand=False` może obcinać narożniki. Miesza test przekrzywienia z utratą treści.
- `x04` łączy od razu 72 dpi, rozmycie i JPEG q25. Przydatny test skrajny, ale nie wyjaśni, który czynnik powoduje błąd.
- `x11` zachowuje **tylko trzy pierwsze strony** długiego odwołania. To także usunięcie stron.
- `x07` arbitralnie dostaje klasę pełnomocnictwa mimo dołączenia przelewu. Nie jest wiarygodnym testem klasyfikacji bez ustalonej polityki.
- Pieczątka i „podpis” są geometryczne, bez naturalnych ubytków i zmienności nacisku.
- `x12` dodaje obraz pieczątki. Nie sprawdza kluczowego przypadku: **wartość potrzebna do JSON istnieje wyłącznie we wklejonym obrazie**.
- Generator używa `pdftoppm`, więc obecnie wymaga narzędzia spoza pip.
- Powstaje 12 przypadków z trzech spraw; brak perspektywy telefonu, faksu i błędnej warstwy OCR.

Najbardziej wartościowe uzupełnienie syntetyki: wydrukować kilka dokumentów i zeskanować/sfotografować je naprawdę. Treść jest znana, więc koszt adnotacji pozostaje mały.

**4. Jak mierzyć i jaki rozmiar ma sens**

Dotychczasowy eksperyment nie mierzył ekstrakcji biznesowego JSON: modele dostawały maksymalnie trzy strony, a ocena dotyczyła klasy, wykrycia problemów i podobieństwa początku transkrypcji. Dodatkowo trafność klasy liczona w `scal.py` obejmuje odpowiedzi ze statusem `ok`, więc awarie trzeba raportować osobno. Źródła: `E/narzedzia/modele.py`, `E/narzedzia/scal.py`, `E/format/wynik_modelu.schema.json`.

Proponowane raporty:

| Raport | Co pokazuje |
|---|---|
| Oryginały / skany / mieszane / błędny OCR / nowe układy / destrukcyjne / negatywy | Osobne wyniki, bez ukrywania słabej grupy w średniej |
| Klasyfikacja | Macierz 4×4, precision/recall/F1 każdej klasy, odsetek negatywów dających dokładnie `{}` |
| Ekstrakcja | TP/TN/FP/FN i F1 dla każdego pola oraz klasy |
| Cały dokument | Odsetek dokumentów z całkowicie poprawnym JSON |
| Pary oryginał–wariant | Spadek F1 i liczba nowych błędów po przekształceniu |
| Przypadki rzadkie | Liczebność i wynik: PESEL, konsorcjum, wielu zamawiających itd. |
| Uruchomienie | Błędy techniczne, niepoprawny JSON, czas p50/p95, koszt i ponowienia |

W ewaluatorze:

1. Waliduj strukturę i typy; brak klucza nie powinien znikać jako poprawny TN.
2. Dopasowuj listy **jeden do jednego po treści**, zachowując związki mocodawca–podpisujący.
3. Zliczaj: poprawna wartość → TP; błędna lub nadmiarowa → FP; brak wymaganej → FN; brak po obu stronach → TN.
4. Według przyjętej reguły błędnej wartości **nie doliczaj ponownie FN**.
5. Licz `F1 = 2TP/(2TP+FP+FN)`; TN pokazuj osobno. Dla zerowego mianownika raportuj jawnie `N/A`.
6. Dla negatywu oceniaj dokładne `{}`; nie twórz sztucznych setek TN z pól niepasujących schematów.
7. Obok wyniku końcowego pokazuj diagnostyczną ekstrakcję przy zadanej poprawnej klasie.

Oficjalna normalizacja i podobieństwo 80% pozostają nieznane. Pokazujcie wynik ścisły oraz jawnie opisane przybliżenie konkursowe. Podstawa: `docs/05-weryfikacja/zasady-f1.md`.

**Rozmiar:** 20 zamrożonych spraw × 3 klasy × (oryginał + 6 wariantów) = **420 PDF-ów**, lecz nadal tylko **20 niezależnych spraw**. To dobry test regresji, słabsza podstawa do deklaracji o ukrytym zbiorze.

Przedziały ufności i porównania liczcie przez bootstrap **całych spraw**, razem ze wszystkimi wariantami. Przy zerze błędów w 60 niezależnych próbach jednostronna granica 95% dla częstości błędu nadal wynosi około 4,9%; przy 20 — około 13,9%. To ilustracja niepewności, nie przedział dla F1.

| Czas | Zadanie | Kryterium zakończenia |
|---|---|---|
| 0–2 h | Zamrożenie referencji, podział spraw, wersjonowanie parametrów; baseline rozwojowy | Każdy wynik wskazuje dokument, referencję i wersję konfiguracji |
