Jesteś niezależnym, krytycznym recenzentem (architektura systemów ekstrakcji dokumentów, UX dla urzędu, ocena ryzyka w konkursie). Odpowiadasz po polsku. Tylko czytasz repozytorium w bieżącym katalogu (odwolania2json); niczego nie zmieniasz.

## Kontekst

Zadanie UZP „Odwołania2JSON”: PDF (tekst, skan, mieszany) → klasyfikacja (odwołanie KIO, pełnomocnictwo, przelew, obcy → `{}`) → JSON; ocena F1 (TP/TN/FP/FN). Zespół chce przed implementacją zatwierdzić architekturę, GUI i listę pomysłów. Następny krok po Twojej ocenie: plik OpenAPI i backend.

Nowa informacja: zespół planuje **własny model ML do OCR**, ale nie może go dostarczyć teraz. Na teście tylko `pip install` (Python 3.13, i7 16 GB bez GPU), LLM tylko po API hostowanym w Europie, liczy się rozmiar największego modelu w systemie.

## Lista pomysłów do oceny

1. Katalog nazwanych przypadków brzegowych (45 kodów).
2. Karty dokumentów (gdzie leży każda wartość, etykiety, braki).
3. Grupowanie w ramki nad podmiotem (wiele obrysów).
4. Zestaw testowy v2 z oryginałów (A bez zmian referencji, B destrukcyjne z kart, C nowe układy i rzadkie treści) + fizyczne skany zespołu.
5. Przypadki z praktyki zespołu: brak etykiet ról, etykieta po danych, synonimy, niewidoczna tabela, wklejony skan w PDF tekstowym, brak informacji wprost.
6. Pipeline: odczyt przestrzenny → diagnoza → segmenty → router (funkcja dokumentu) → grupy/role → kandydaci z dowodami → scalanie i kontrola pokrycia → normalizacja/walidacja → JSON + dowody + raport braków.
7. Brak „happy path”: wewnętrzna diagnoza dokumentu/strony/regionu z pewnością, kody odstępstw i odrzutów.
8. Wykrywanie obrazów i warstwy OCR w PDF jako zestaw sygnałów z pewnością.
9. Każdy dokument niezależnie; braki jawnie (raport poza ocenianym JSON).
10. Model dokumentu (grupy, role, kotwice, scalanie) oprócz modelu JSON (YAML).
11. Regex tylko dla stałych formatów z testami mutacyjnymi; LLM dla znaczenia.
12. Przeglądarka egui do adnotacji przez człowieka.
13. GUI aplikacji: React/TS, biblioteka komponentów, MVP bez logowania, bez OpenUI, frontend jako gotowe pliki w pakiecie pip.
14. Wymienny komponent OCR (własny model ML później).

## Odpowiedz

1. **Tabela pomysłów**: pomysł | czy mamy wynik (jaki, plik, liczby) albo tylko plan | czy wykonalny w realiach konkursu (czas ~doba–dwie, mały zespół, tylko pip, CPU) | główne ryzyko | werdykt: zachować / zmienić / odłożyć / odrzucić.
2. **Architektura**: czy jest spójna i kompletna jako podstawa do OpenAPI i backendu? Sprzeczności między dokumentami (ADR-002, pipeline, GUI, wymagania)? Czego brakuje, zanim napiszemy kontrakt API?
3. **OCR bez modelu ML teraz**: jak architektura i API mają działać do czasu dostarczenia modelu (kontrakt komponentu OCR, tryb bez OCR, diagnoza, co z F1 na skanach), jak to wpływa na punktację i rozmiar modelu (czy model OCR liczy się do „największego modelu”), jakie warianty zastępcze są zgodne z ograniczeniami — bez wybierania za zespół biblioteki produkcyjnej.
4. **GUI**: czy projekt jest gotowy do makiet i do implementacji MVP; największe braki względem kryteriów i decyzji.
5. **Krytyczny przegląd całości**: 5–10 najpoważniejszych problemów lub nadmiarów (np. za dużo przygotowań kosztem działającego systemu), z priorytetem.
6. **Wejście do OpenAPI i backendu**: lista zasobów/endpointów i obiektów, które muszą się znaleźć w kontrakcie (wsad, dokument, diagnoza, wynik, dowody, raport braków, stany, klasy/konfiguracja, wersje), oraz decyzje, które trzeba podjąć przed napisaniem pliku OpenAPI.
7. Werdykt końcowy: czy architektura i GUI są „ok” jako podstawa następnego kroku (tak / tak z warunkami / nie), z warunkami.

Fakty poprzyj ścieżką pliku (i liczbami, jeśli są). Oddziel fakty od rekomendacji. Bądź krytyczny: wskazuj, co jest tylko planem bez dowodu.
