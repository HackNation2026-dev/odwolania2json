## 2. Architektura

**Spójność:** kierunek jest spójny między ADR-002, oceną pipeline'u i UI 0.2.0. Stany wyniku, dowody poza JSON, niezależność dokumentów i wspólny silnik dla CLI i GUI zgadzają się. Jako podstawa kontraktu architektura nie jest kompletna.

**Sprzeczności (fakty):**
- `docs/04-architektura/README.md` nadal podaje „Dostarczenie: Docker”, moduł Rust i „GUI opcjonalne”; ADR-002 mówi pip, bez Rusta, GUI obowiązkowe. Podobnie `pelna-aplikacja.md`.
- `docs/03-wymagania/README.md`: tabela UZP-15 „GUI opcjonalne”, uzupełnienie „obowiązkowe”; UZP-02 analogicznie.
- ADR-002 pkt 15 „prawdopodobnie Next.js” wobec `projekt-ui.md` §8.1 „bez serwera Next.js u jury”.
- ADR-002: „najpierw zestaw testowy, dopiero potem budowa” oraz „najpierw F1, GUI po stabilnym F1”. Planowany następny krok to OpenAPI i backend, a zestawu, loadera i ewaluatora (pkt 13–14) nie ma.
- ADR-002 pkt 11 (błąd techniczny = brak pliku) wobec wymogu README: JSON dla każdego pliku wejściowego. Nie wiadomo, jak ewaluator traktuje brak pliku.
- UI §3.1 deklaruje „Skany… są obsługiwane (OCR)” przy braku OCR (wskazane też w `ocena-ui-vs-kryteria.txt`).
- Kody: katalog używa `snake_case` po polsku, UI pokazuje `LLM_TIMEOUT`. ADR wymaga kodów odrzutów w katalogu, a tam ich nie ma.

**Braki przed kontraktem API (rekomendacja):** kontrakt odczytu (strona, słowa, bbox, źródło, pewność, układ współrzędnych), schemat diagnozy, schemat dowodu i raportu braków, enum stanów i kodów wykonawczych, model wykonania zadań (synchroniczny czy asynchroniczny, trwałość), tożsamość wersji (silnik, konfiguracja, prompt, model), polityka `null` i polityka wielu dokumentów w PDF.

## 3. OCR bez modelu teraz

**Fakty:** test zawiera skany i dokumenty mieszane (`odpowiedzi-mentora`). 0/180 pozytywów to skany; 3 z 12 negatywów to skany, 1 jest mieszany (`eksperyment-przypadki-brzegowe`). Lokalny model przez pip nie jest ani potwierdzony, ani wykluczony (`pytania-otwarte.md`). README wymaga wyłącznie komponentów open source.

**Kontrakt komponentu (rekomendacja):**
- Wejście: obraz strony lub regionu, DPI, wskazówka orientacji.
- Wyjście: linie i słowa z bbox w układzie obrazu, pewność, zastosowany obrót, wersja dostawcy.
- Metadane: `dostepny`, `nazwa`, `wersja`, `liczba_parametrow`, `licencja`, `lokalizacja`.
- Odczyt warstwy tekstowej PDF powinien implementować ten sam model wyjścia, żeby reszta pipeline'u nie rozróżniała źródła.

**Tryb bez OCR:** dostawca „brak” zwraca `dostepny=false`. Diagnoza nadal oznacza strony i regiony wymagające OCR. Pola z takich stron dostają powód „nieprzetworzone”, dokument stan „częściowy”, a dokument czysto skanowany osobny kod (np. `ocr_niedostepny`), nigdy „obcy”. API wystawia gotowość OCR, a UI warunkuje teksty.

**F1:** bez OCR każdy pozytywny skan daje same FN, niezależnie od tego, czy zapiszemy `{}`, czy nic. Dla negatywów-skanów `{}` jest poprawne, a brak pliku nie. Decyzja zespołu: czy CLI w trybie konkursowym zapisuje `{}` z jawnym wpisem w raporcie, czy nie zapisuje pliku. Rekomenduję zapytać mentora, a do odpowiedzi zrobić to przełącznikiem.

**Rozmiar modelu:** README mówi o „mocy modelu LLM… w bilionach parametrów”; mentor o „największym modelu”, bez przelicznika (U-Q07). Klasyczny model OCR (dziesiątki milionów parametrów) nie będzie największy przy żadnej interpretacji. Model wizyjno-językowy użyty jako OCR jest LLM-em i prawdopodobnie stanie się największym modelem systemu. Warto zadać to pytanie mentorowi.

**Warianty zastępcze zgodne z ograniczeniami (klasy rozwiązań):**
- **Lokalny OCR na CPU z wagami w kole pip**, bez binarek systemowych, na otwartej licencji. Do sprawdzenia: koła dla Pythona 3.13 na Windows i Linux, jakość polskich znaków, czas na i7.
- **Model wizyjny przez API w Europie.** Liczy się do rozmiaru; dochodzą koszt, czas i wysyłanie obrazów na zewnątrz.
- **Własny model zespołu jako usługa na serwerze w UE.** Discord dopuszcza własny serwer; ryzykiem jest dostępność endpointu w czasie testu.
- **OCR z binarką systemową** odpada przy „wyłącznie pip”.

W eksperymencie trzy modele wizyjne przepisały początek strony z podobieństwem 0,966–0,973, ale żaden nie jest dopuszczalnym modelem docelowym, a pomiar objął ok. 200 znaków z najwyżej 3 stron.

**Warunek:** własny model to ulepszenie, nie zależność. Dostawca zastępczy musi działać przed zgłoszeniem i być zmierzony na grupie A.

## 5. Najpoważniejsze problemy

1. **[P0] Brak pomiaru F1 ekstrakcji.** Wszystkie wyniki dotyczą kontraktu, lokalizacji referencji albo klasyfikacji modelami niedopuszczalnymi.
2. **[P0] Brak OCR i odczytu PDF** przy 100% F1 w preselekcji i potwierdzonych skanach w teście.
3. **[P0] Brak wybranego modelu LLM.** Żaden otwarty model hostowany w Europie nie został zmierzony. MiniMax działa z `api.minimax.io` i nie spełnia wymogu bez weryfikacji; Codex i Claude są zamknięte. Wynik „trafność klasy 0,976–1,0” nie przenosi się na model docelowy.
4. **[P0] Przygotowania przewyższają produkt.** Jest 14 stron UI, 56 ramek, 45 kodów, 4 konsultacje i przeglądarka w Rust, a brakuje loadera, ewaluatora i CLI zaakceptowanych w ADR-002.
5. **[P1] Projektowanie pod dokumenty z praktyki zamiast pod generator testu.** Karty pokazują, że 100% wartości referencyjnych występuje w tekście dosłownie lub w innym zapisie. Realne ryzyko dla F1 to skany, role, pierwszy zarzut i normalizacja.
6. **[P1] Zestaw testowy v2 nie istnieje**, a obecne syntetyki mają znane wady i pochodzą z 3 spraw.
7. **[P1] Pipeline 9-etapowy bez ablacji.** Każdy etap LLM to czas i ryzyko; duży model „awaryjnie” podnosi rozmiar największego modelu.
8. **[P1] Nierozstrzygnięte zasady wyniku:** `null` wobec pól wymaganych, brak pliku wobec `{}`, wiele dokumentów w PDF, kanał klucza dla jury (U-Q04).
9. **[P2] Nieaktualne dokumenty architektury** (Docker, Rust, GUI opcjonalne) obok ADR-002.
10. **[P2] Dwa katalogi przypadków podają sprzeczne liczby** (T1, T2 wobec katalogu kodów).

## 6. Wejście do OpenAPI i backendu

**Zasoby (rekomendacja minimalna):**

| Zasób | Endpointy |
|---|---|
| System | `GET /health`; `GET /system` (wersje silnika i konfiguracji, rewizja kontraktu, lista modeli z parametrami, licencją i regionem, największy model, gotowość LLM i OCR, limity) |
| Wsad | `POST /batches` (multipart, ścieżki względne), `GET /batches/{id}`, `POST /batches/{id}/retry` |
| Dokument | `GET /documents/{id}` (postęp, stan wyniku, klasa, kody), `/file`, `/pages/{n}/image`, `/pages/{n}/text` |
| Diagnoza | `GET /documents/{id}/diagnosis` (dokument i strony; regiony opcjonalnie) |
| Wynik | `GET /documents/{id}/result` (dokładnie oceniany JSON), `/evidence`, `/report` |
| Klasy | `GET /classes`, `GET /classes/{id}` (YAML + JSON Schema); przeładowanie poza MVP |
| Słowniki | `GET /codes` (kody wykonawcze z opisami) |

**Obiekty:**
- `Batch`, `Document`, `Diagnosis`/`PageDiagnosis`, `ClassDecision` (kandydaci, sygnały za i przeciw).
- `Field` (ścieżka, stan, metoda, powód braku), `Evidence` (strona, cytat, `bbox[]` opcjonalne, źródło tekst/OCR, reguła i przesłanki), `GapReport`.
- `TechnicalError` (etap, kod, możliwość ponowienia), `Versions`, `OcrProviderInfo`, `ModelInfo`.
- `Result` jako obiekt dowolny, walidowany schematem klasy, nie typowany na sztywno w OpenAPI.

**Decyzje przed napisaniem pliku:**
1. Przetwarzanie synchroniczne czy zadania z odpytywaniem; pamięć czy pliki na dysku. Rekomenduję zadania + katalog roboczy, bez bazy.
2. Enum stanów: postęp osobno od stanu wyniku; które z sześciu stanów trafiają do v1.
3. Polityka `null` dla pól nienullowalnych w YAML.
4. Brak pliku czy `{}` przy błędzie lub braku OCR w trybie konkursowym.
5. Wynik dla wielu dokumentów w PDF.
6. Układ współrzędnych i jednostki bbox; geometria opcjonalna w v1.
7. Konwencja i lista kodów wykonawczych, mapowanie na katalog 45.
8. Kontrakt dostawcy OCR i jego metadane.
9. Klient LLM: dwa protokoły (ADR-002 pkt 7), co wchodzi do klucza cache i wersji.
10. Język nazw w API (polskie klucze kontraktu wobec angielskich pól technicznych).
11. Kanał klucza API i zachowanie przy 401, limicie i braku sieci.
