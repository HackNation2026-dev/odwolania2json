# Recenzja architektury: UZP „Odwołania2JSON” i COI „Cyfryzacja Formularzy”

Wynik w skrócie: w obu zadaniach zalecam rdzeń w Pythonie bez własnego kodu Rust. UZP to czysty pakiet pip z hybrydą reguł i małego modelu po API w UE. COI to FastAPI z lokalnym modelem i parserem dokumentów w osobnych kontenerach oraz frontendem React. Niczego nie uruchamiałem ani nie mierzyłem; liczby dotyczące RAM i czasu są szacunkami.

Obserwacje z materiałów, których nie ma w Waszych docs:
- Wzorzec `oczekiwane-json/odwolanie.json` to JSON z komentarzami i brakującym przecinkiem po `pelnomocnik.nazwa` (linia 18). Nie da się go parsować wprost.
- Typy w referencjach: `kwota` i `przez-pelnomocnika` to liczby, a `numer_bzp` jest znormalizowany bez spacji (`2026/BZP00999778`). `pesel` jest liczbą tylko we wzorcu; w przykładzie 01 ma wartość `null`.

### 2. Tabela decyzji

Uzasadnienie: dokumenty testowe są syntetyczne (Discord 12:47), więc reguły dadzą stabilny wynik na polach formalnych. Model może być wtedy mały, co punktuje w finale.

### 3. Rola Rusta

Rezygnacja z własnego kodu Rust. README wymaga rozwiązania „opracowanego w Python 3.13+” z instalacją pip, a ocena jest zautomatyzowana. Rozszerzenie Rust wymagałoby gotowych kół dla systemu jury (wzmianka o `.bat` sugeruje Windows) albo toolchaina. Czas zdominuje wywołanie sieciowe LLM, więc nie ma czego przyspieszać. Pytanie U-Q06 przestaje być potrzebne.

### 5. Model i inferencja

- Na laptopie jury nie działa żaden LLM. Lokalnie pracuje tylko OCR na CPU, rzędu setek MB RAM (szacunek).
- Kandydat startowy: Bielik. Karta `Bielik-11B-v2.3-Instruct` podaje Apache 2.0 i 11 mld parametrów; repo GGUF dopisuje „Terms of Use”. Karta `Bielik-4.5B-v3.0-Instruct` podaje Apache 2.0 według wyniku wyszukiwania.
- Dostawca: dokumentacja CloudFerro Sherlock wymienia `speakleash/Bielik-11B-v3.0-Instruct` pod API zgodnym z OpenAI (wynik wyszukiwania). Lokalizacji serwerów, licencji v3 i obsługi JSON Schema nie potwierdziłem.
- Scaleway Generative APIs deklaruje hosting w Europie; listy modeli nie potwierdziłem.
- Zmierz własne F1 dla 2–3 rozmiarów modelu i wybierz najmniejszy, który nie traci jakości. Preselekcja to 100% F1, więc jakość ma pierwszeństwo.
- Awaria API ma dawać błąd techniczny z ograniczonym ponawianiem, nigdy zgadywane dane.

### 6. Docker

Docker jest tu dodatkiem, nie drogą dostarczenia. Jury instaluje przez pip i uruchamia komendę. Jeśli go dodasz dla GUI: `python:3.13-slim` z przypiętym tagiem, `USER` nieuprzywilejowany, bez modelu w obrazie, klucz przez env. Obowiązkowo przetestuj czysty `venv` i `pip install -r requirements.txt` na Windows i Linux.

### 7. Ryzyka formatów

- OCR: uruchamiaj tylko, gdy strona nie ma warstwy tekstowej. Skany w ukrytym teście są niepotwierdzone (U-Q08).
- Zakres stron: README mówi o informacjach „z reguły na pierwszych trzech stronach”, ale podpisujący pełnomocnictwo bywają na końcu. Nie ucinaj na ślepo.
- JSON: końcowy plik zawsze serializuje kod (Pydantic, stała kolejność kluczy, `null` zamiast braku klucza), nigdy model.
- Pusty wynik: domyślnie `{}` w pliku o nazwie wejścia, z przełącznikiem w konfiguracji. To moja interpretacja, do potwierdzenia u mentora.
- F1: algorytm 80% jest nieznany. Własny ewaluator (np. `rapidfuzz.ratio` i dopasowanie list po podobieństwie) jest tylko przybliżeniem.

### 8. GUI

Potrzeba to wgranie PDF, uruchomienie analizy i widok PDF obok JSON (FAQ 12b). Wystarczy jeden ekran: natywny podgląd PDF w przeglądarce i panel JSON. React/TypeScript jest w porządku pod warunkiem, że zbudowany `dist` leży w repo i jury nie potrzebuje Node. egui odrzucam: nie znam dojrzałego komponentu PDF dla egui, a wymóg Pythona go wyklucza. GUI jest warte najwyżej 10 pkt, więc rób je na końcu.

### 9. Kolejność implementacji

1. Loader 60 spraw i własny ewaluator F1 z podziałem według spraw.
2. CLI `input` → `output` z odtworzeniem drzewa i pustym wynikiem.
3. Ekstrakcja tekstu i klasyfikacja regułowa, w tym dane negatywne.
4. Przelew samymi regułami.
5. Pełnomocnictwo i odwołanie: YAML → schemat → LLM → normalizatory.
6. Zapasowy OCR.
7. Porównanie rozmiarów modeli.
8. Demonstracja czwartej klasy dodanej samym YAML-em.
9. Raport dowodów (fragment źródłowy dla pola) poza ocenianym JSON-em.
10. GUI.
11. Test czystej instalacji i przekazanie klucza.

### 10. Uwagi do ADR-001

- ADR nie zawiera decyzji, tylko odsyła do architektury. Brakuje bibliotek, modelu, dostawcy i strategii ekstrakcji.
- „Rust: istniejący moduł pomocniczy” należy usunąć. To ryzyko bez korzyści.
- „Dostarczenie: Docker” jest błędne jako ścieżka główna.
- `pelna-aplikacja.md` jest wklejony z COI (wzmianka o CDN w COI, układ `apps/`, `packages/`). Dla UZP ten układ koliduje z wymogiem `input`, `output` i `requirements.txt` w katalogu głównym.
- Brakuje decyzji o pustym wyniku i odnotowania wadliwego wzorca `odwolanie.json`. Nagłówek wersji 0.1.0 nie zgadza się z repo 0.2.1.

Kod powinien tworzyć UUID-y, `techName`, siatkę, przepływ, stronę `FINISH` z `INFO_SECTION` i JSONatę z szablonów. Adaptery trzymaj za interfejsem, żeby dało się podmienić Tika na Docling.

### 5. Model i inferencja

- Sprzęt jest nieznany (C-Q07). Projektuj pod CPU i 16 GB.
- Model domyślny: Bielik 4.5B v3 Instruct w GGUF, kwantyzacja Q4 lub Q5, około 3–4 GB RAM (szacunek). Ścieżka modelu jest konfigurowalna, z opcją Bielik 11B Q4 (około 7 GB, szacunek) na mocniejszej maszynie. Warunki „Terms of Use” w repo GGUF trzeba przeczytać.
- Czas: na CPU spodziewaj się minut na formularz (szacunek). Pomagają zwarty model pośredni, przetwarzanie stronami i limit tokenów.
- Zbuduj tryb heurystyczny bez LLM, który zawsze zwraca poprawny JSON. To zabezpieczenie na obronę przy słabym sprzęcie.
- Wagi pobieraj przy budowie obrazu albo montuj jako wolumen. W runtime nie może być sieci; testuj z siecią `internal`.

### 6. Docker

Compose z czterema usługami:
- `api`: `python:3.14-slim` przypięty tagiem i digestem. Alpine jest możliwy tylko bez `onnxruntime`, bo jego koła wymagają glibc 2.28+ (sprawdzone).
- `tika`: zbudowany z oficjalnego `eclipse-temurin:21-jre` z jarem Tika i Tesseractem. Gotowy obraz `apache/tika` nie jest „Docker Official Image”, więc warto dopytać o interpretację „oficjalnych obrazów”.
- `llm`: llama.cpp zbudowany wieloetapowo na oficjalnym obrazie Debiana.
- `web`: nginx w wariancie Alpine, nieuprzywilejowany, albo statyki serwowane z `api`.

Wszędzie `USER` bez uprawnień roota, `read_only` i `tmpfs` na `/tmp` (to realizuje też wymóg plików tymczasowych). Publikuj jeden port, sidecary trzymaj w sieci wewnętrznej, sekret JWT podawaj przez env. Rozmiar zdominuje model (3–7 GB), więc lepiej trzymać go w wolumenie.

### 7. Ryzyka formatów

- DOC: w materiałach są rozszerzenia `.DOC` wielkimi literami; sygnatura OLE jest wspólna z XLS, więc sprawdzaj typ po zawartości.
- DOCX, XLSX i ODS to archiwa ZIP: weryfikacja MIME musi zajrzeć do środka i mieć limity rozpakowania.
- ODS i XLSX to formularze rysowane komórkami: trzeba czytać scalenia i kolejność.
- OCR: jakość skanów JPG/PNG, obrót, pola wyboru jako glify. `.JPE` z materiałów odrzucaj do decyzji C-Q08.
- JSON: trzymaj się pisowni z przykładów (`repeatingSectionGrid`, `MAIN`/`FINISH`), bo §3.2 wskazuje je jako oczekiwany wynik. Zrób z tego przełącznik w konfiguracji do czasu odpowiedzi na C-Q01–03.
- JSONata: generuj z szablonów z dokumentu reguł, sprawdzaj składnię i istnienie wskazanych `techName`.
- Walidator semantyczny jest obowiązkowy, bo schemat niczego nie sprawdza.

### 8. GUI

React/TypeScript jest tu uzasadniony. Potrzebne są trzy widoki: upload, podgląd źródła obok JSON oraz renderer e-usługi z JSON. Specyfikacja definiuje układ wprost jako CSS (`grid-area: {y+1}/{x+1}/span rows/span cols`), a stany `SHOW`/`READ_ONLY` można liczyć na żywo biblioteką `jsonata`. Renderer pokrywa rozszerzenia IV i V oraz „intuicyjność” (20%). egui odrzucam: wymagałby odtwarzania siatki CSS, kontrolek formularza i dostępności na canvasie.

### 9. Kolejność implementacji

1. Kompilator modelu pośredniego do JSON COI i walidator semantyczny, sprawdzone na dwóch referencjach.
2. Szkielet REST: walidacja pliku, katalog tymczasowy, JWT, Docker bez roota.
3. Adaptery ośmiu formatów na dziewięciu formularzach.
4. Ekstraktor heurystyczny bez LLM.
5. Kontener LLM z gramatyką.
6. Regułowe mapowanie słowników, danych inicjalnych (`PESEL.name` itd.) i walidatorów (PESEL, NIP, REGON, EMAIL, ZIP_CODE).
7. Zależności i JSONata.
8. Upload i podgląd JSON.
9. Renderer e-usługi.
10. Test bez sieci, wynikowe JSON-y dla formularzy 2–4 i 6–9, README, dokument architektury, slajdy, film.

### 10. Uwagi do ADR-001

- Dokument jest identyczny jak w UZP i nie zawiera decyzji.
- „API: Rust/Axum, jeśli gotowa baza” należy usunąć.
- Brakuje strategii generacji (kompilator czy LLM), wyboru adaptera DOC, runtime'u modelu i progu sprzętowego.
- COI-12 traktuje JWT tylko jako parametr. Zalecam faktyczną walidację tokenu z możliwością wyłączenia.
- COI-11 pomija oficjalne obrazy, preferencję Alpine, porty i sekrety w runtime.
- `rozbieznosci.md` nie odnotowuje, że przykłady rozstrzygają pisownię, ani niezgodności nazw słowników.
